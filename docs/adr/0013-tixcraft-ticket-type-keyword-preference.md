# tixcraft 票種關鍵字是「優先」不是「把關」：未命中改依 mode 挑選

2026-11-21 的 ARTMS 台北場實戰：區域關鍵字 `VIP` 選區正常（命中 1F VIP區4980），進到票種頁卻永遠選不到票。該頁可用的票種只有「全票+福利兌換券 4,980」與「全票 4,900」，而 tixcraft 的票種選擇沒有專屬關鍵字，`nodriver_tixcraft_assign_ticket_number` 直接拿區域關鍵字比對票種名稱——全數未命中；使用者的 `area_auto_fallback` 是關的，舊邏輯在 strict 模式下直接回「No ticket type selected」，上層再把這個失敗誤報成「Ticket count 2 unavailable」退回選區，形成同區同頁同結果的無限循環。區域叫 VIP區、票種叫全票，是主辦方的命名落差，不是缺票。

我們決定（#106）：票種關鍵字比對保留，但只作優先序——第一個命中的票種先選；全數未命中時不再失敗，直接依 `auto_select_mode` 從可用票種中挑一張，且這個回落不受 `area_auto_fallback` 控制（該設定只管選區頁）。唯一的硬過濾是 `keyword_exclude`：它在收集候選時就剔除，任何路徑都選不到。assign 的回傳同時多帶失敗原因（reason），讓「本區無可用票種」（`no_valid_types`：全數 disabled／售完，或被 exclude 剔光）與「張數不足」在 log 與退回計數上分開，不再互相冒名；兩者的退回行為（回選區重選）不變。

## Considered Options

- **票種完全不做關鍵字比對，只剩 exclude 過濾**：模型最簡單，但拿掉了「票種名含關鍵字時優先選它」的既有能力——例如票種真的叫「VIP票」時，確定性優先比 mode 隨機挑更符合意圖。使用者裁決：比對跟排除都要留，否決。
- **新增獨立的票種關鍵字設定，strict 把關保留**：等於要使用者為票種再輸入一次關鍵字（本案就得補「全票」），而他的模型是「區域命中後，除了避開的都可以買」；且設定面多一個欄位多一份維護，否決。
- **未命中回落繼續受 `area_auto_fallback` 控制**：本案事故正是 fallback 關閉的組合；讓票種頁跟著選區頁的 strict 設定一起失敗，等於保留地雷，否決。

## Consequences

- 區域關鍵字若湊巧出現在不想買的票種名裡，該票種會被優先選中——用 `keyword_exclude` 排除即可，這本來就是 exclude 的職責。
- mode 為 random 時，同區多張可用票種是隨機出一張（例如 4,980 福利版與 4,900 純全票）；要確定性就用 exclude 收斂到一張，或把 mode 改成 from top。
- log 現在能分辨票種是「關鍵字命中」還是「mode 挑選」，以及失敗是「無可用票種」還是「張數不足」——下次同類卡關看 log 即可定性，不必再人工追 code。
