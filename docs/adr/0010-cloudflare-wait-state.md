# Cloudflare 驗證自動處理失敗後，主迴圈進入等待狀態而非繼續 dispatch

Cloudflare 人機驗證（ibon 的「會員您好，正在驗證您是否是人類」）會在搶票過程的任意時刻出現，不限於頁面載入當下（upstream issue #433 的回報）。主迴圈原有的防護有兩個缺口：偵測只在 URL 變化時執行，同一個 URL 中途跳出的驗證不會被發現；且每個 URL 的自動處理（`handle_cloudflare_challenge`）失敗 3 次後就放棄，平台 handler 照常在驗證頁上操作與刷新——驗證頁本就需要人工完成，在上面持續操作既不會有進展，還可能觸發站方的速率限制。

我們決定（#100）：自動處理的預算（每 URL 3 次）用盡後，主迴圈進入**等待狀態**——停止該分頁的一切 dispatch 與頁面操作，每約 3 秒只做偵測探測；進入時印出醒目橫幅並（在票券音效啟用時）播放一次提示音，等待期間每約 60 秒 log 提醒一次。探測不到驗證、或 URL 已離開該頁，即自動恢復並重置失敗計數；不設硬性逾時（逾時後恢復操作正是要避免的風險）。等待是逐 pass 判斷的迴圈狀態而非阻塞式等待，退出與暫停檢查照常有效。偵測另加週期性重檢（每約 200 pass），補上同 URL 中途出現的驗證。等待狀態的決策邏輯放在 `nodriver_common`（`new_cf_wait_state`／`cf_wait_step` 等），與 `close_stale_tabs` 同例，使其不需瀏覽器即可測；cityline／kktix 登入頁的既有排除不變。

## Considered Options

- **維持現狀（失敗 3 次後照常 dispatch）**：驗證頁上空轉、可能招致站方限制，且使用者無從得知需要介入，否決。
- **等待但設硬性逾時，逾時後恢復自動處理與 dispatch**：逾時只是把「在驗證頁上操作」延後重演，且人工驗證可能因故需要數分鐘，否決。
- **偵測到驗證立刻等待、跳過自動處理**：許多 managed challenge 幾秒內自動通過、或一次點擊即解，現行自動處理成功率不低；太早放棄反而讓每次小驗證都要人工介入，否決。

## Consequences

- 若偵測誤判（false positive），bot 會閒置到 URL 變化或探測轉陰為止：等待狀態的離開條件有二（探測轉陰、URL 變化），且探測是既有的三層偵測，誤判率與現行自動處理的觸發率相同，不另引入新的誤判面。
- 主迴圈每約 200 pass 多一次完整偵測（一次 target 掃描＋至多兩次 evaluate），換取中途驗證的可偵測性；等待期間的探測頻率（約 3 秒一次）遠低於主迴圈本身的 pass 頻率。
- 平台模組不需要知道等待狀態的存在：dispatch 被主迴圈整段跳過，恢復時平台流程從當前頁面狀態自然接續。
